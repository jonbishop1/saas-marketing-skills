# Reusable brief

| Field | What to capture |
| --- | --- |
| Product and task | Input → useful output; present workflow or workaround |
| Product class | Developer tool, data product, or both; what that changes |
| People | User, evaluator, champion, buyer, reviewer; evidence for each |
| Adoption motion | Local / open source / hosted / API / enterprise |
| First meaningful value | Observable result; excludes setup alone unless setup is the actual value |
| Durable adoption | Repeat use, team deployment, production workload, or another justified milestone |
| Constraints | Deployment, access, integrations, resources, geography, ownership |
| Evidence | Supplied / observed / hypothesis; source and limits |
| Decision | Current goal, next action, and the fact that could change it |

## Two fictional examples

**TraceNest, developer tool:** a backend engineer wants to reproduce a failed request locally. A successful sample replay shows the interface works; a sanitized replay from their own service tests usefulness. A team policy blocks uploading production payloads. Recommend a local evaluation path before a generic hosted-trial campaign.

**FlowLake, data product:** a data engineer wants reliable incremental warehouse ingestion. A sample connector run proves setup, not correctness under late arrivals. The platform owner controls credentials and the analytics lead validates reconciliation. An evaluation needs an approved dataset, freshness and reconciliation criteria, and a cost envelope.

## Routing

Use audience research for segment selection, marketing plan for sequencing, onboarding for first value, and data-product-evaluation for a bounded proof of value. Keep these tasks distinct from collecting a comprehensive company biography.
