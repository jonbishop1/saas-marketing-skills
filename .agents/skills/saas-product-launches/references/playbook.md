# Launch brief

New task / audience / availability / supported environments / demonstration / limitations / evaluation path / support owner / primary channel / success / stop or rollback condition.

## Readiness distinctions

A developer package with working installation but no maintainer support path may be ready for a narrow experiment, not a broad team-adoption claim. A data connector tested only on a sample can be announced with that scope; it cannot support an unqualified production-readiness claim.

## Release assets

Keep the announcement, docs, quickstart, pricing, and actual access behavior consistent. For a feature, explain the affected workflow and migration requirements. Include a recovery or rollback path if the change can disrupt existing work.

## Follow-up

Review failed evaluations and support themes alongside usage. A quiet launch with useful qualified feedback may meet a learning objective; a high-traffic launch with broken setup has a readiness problem.
